## Slice 3, in one sentence

A bill can no longer be paid to a name a payer typed once and everyone hoped was right: vendors are records with KYC and versioned, encrypted bank details that the accountant maintains and the payer verifies against the bill before money moves, duplicate bills are stopped by two structural database guarantees rather than a UI warning, and every queue shows ageing, an unanswered query, a due date closing in, a repeat amount, and a bank-just-changed flag — computed live, never cached by hand.

## Scope, decided before this slice started

AGENTS.md's own build order names slice 3 as "vendor records with KYC and versioned bank details, payer verification, payment history, computed flags." Three things are explicitly **out**, all confirmed with the user directly rather than assumed:

- **The brief's §09 in full** — advances, part-payments, a running per-request settlement ledger, TDS netted across payments, an "invoices awaited" chase queue, refund-due tracking. Not designed, not stubbed, not referenced anywhere in this slice. It isn't named in AGENTS.md's slice-3 sentence, and it's large enough to roughly double this slice on its own. `payment`'s existing `UNIQUE(request_id)` (one payment per request) is untouched by anything in this document.
- **§08's sixth duplicate verdict, "matched an open advance."** Five of six are built (paid/hard-block, open/warn, rejected/escalate, held/link, nothing/silent). The sixth only makes sense once a request can be part-paid, which needs §09.
- **Perceptual-hash duplicate detection.** `request_file.phash` exists (reserved since phase 1) but nothing computes it, and no image-processing capability exists anywhere in this codebase yet. It converges naturally with slice 4's extraction work, which already has to look at the image. Duplicate control in this slice ships with four of five signals — vendor+invoice identity, file checksum, vendor+amount+date window, payment reference — not five. `phash` stays reserved-but-unpopulated.

## Things found and resolved along the way

**1. Resubmit-after-rejection needs a different mechanism than `resubmit`, and a schema column that doesn't exist.** The existing `resubmit` transition (`src/requests/transitions.ts`) only ever fires from `stage: 'raised'` and bumps `revision` on the *same* request — that's "returned for correction," a different brief concept from "a bill rejected outright, then reconsidered." The brief's own mockup (§08) shows reconsideration going through the normal capture flow as a **brand-new request** with a new `ref`, `request.linkedRequest` pointing back at the original — a column reserved, unused, since phase 1 for exactly this. Routing "back to the approver who declined it" needs a capability this codebase has nowhere else: a specific person attached to one request instance, distinct from the shared-department-pool model everything else uses. Designed narrowly in phase 11: a soft routing hint (a banner, a queue-sort nudge), never enforcement — deliberately avoiding reopening "assigned approver" semantics everywhere else, and avoiding making a request un-actionable the moment one specific person is away (still-unresolved, org-wide, since slice 1).

**2. `accountRequest` currently accepts a request with no vendor at all — this slice makes that a hard requirement.** `accounting` has no `vendorId` column today; `request.vendor` (free text from capture) is never touched by accounting. AGENTS.md's own lifecycle description says stage 3 is "head, voucher, company. **Vendor matched or created**." A real behavior change to an already-shipped transition, named here rather than slipped in as a side effect of adding a new table.

**3. §11's "payer: edit vendor bank (partial)" capability isn't in tension with §10's "KYC and bank from the accountant" — it's the escape hatch for the moment a payer is physically holding fresh proof and routing back through accounts first would be exactly the friction AGENTS.md's own override philosophy warns against** ("the check is wrong and it's blocking a real payment... always an override path"). Designed as two RLS-distinct `INSERT` paths on `vendor_bank` (phases 9 and 10), not a UI toggle on one form.

**4. `verified_by`/`verified_at` on `vendor_bank` are set by the payer, confirmed from the brief's own audit-trail example (§14/§07)** — "Vendor bank verified · Suresh Pillai," a payer, as its own Trail entry distinct from "Accounted · Kavya Rao." Never backfilled by whoever entered the bank record. This is what makes "a bank change flags every open request" a live read at pay time rather than a per-request cached flag — see phase 10.

**5. `payment.reference`'s existing unique index (phase 4) is case-sensitive** — a UTR retyped in different case passes as "different" today, which quietly undermines the one duplicate signal §08 calls decisive with no listed miss case. Fixed to be case-insensitive in phase 11, named explicitly since it's a real gap inside the very feature phase 11 builds around it, not a drive-by fix.

**6. `head_of_account`'s own header comment already named a cheap slice-3 pickup**: "the brief's 'suggested from the vendor's last 3 bookings' needs vendor master data (slice 3) — skipped here, not faked." Once `vendor.defaultHeadId` exists, the accountant's head-of-account field can prefill from it on a vendor match — a one-field convenience folded into phase 9, not its own line of scope.

**7. The GST-status / 206AB-compliance / lower-deduction-certificate fields shown in §10's vendor mockup are cut entirely.** They imply an external compliance-checking integration that doesn't exist anywhere in this codebase and isn't named in AGENTS.md's own slice-3 sentence. Manual-entry fields for data nothing actually checks would be UI theater, not KYC — left out, not stubbed, a later slice's job if a real integration ever gets built.

## Design decisions

**Vendor schema.** Three new tables: `vendor`, `vendor_bank`, `vendor_document`. `vendor.vendorKey` is a **generated column** (`coalesce(gstin, pan, id::text)`) — same-row, deterministic, can never drift from a hand-maintained duplicate. Partial unique indexes on `gstin`/`pan` (nullable-safe, so a vendor with neither doesn't collide) are the actual concurrency guarantee against two people creating "the same" vendor at once — a UI lookup can't stop that race (AGENTS.md rule 7's own reasoning, applied to vendor identity as well as invoices). `vendor_bank` is versioned via `supersededAt`, mirroring `accounting`'s own "latest row wins, never update" pattern, with a partial unique index enforcing at most one current row per vendor. `vendor_document` is its **own table**, not folded into `request_file` — despite the surface-level similarity (both are presigned-upload evidence rows with a `kind`), `request_file`'s entire RLS shape is built around "this row belongs to a request," and a vendor's GST certificate isn't tied to any bill; forcing a second, orthogonal scoping axis onto an already-shipped, security-relevant table isn't worth the reuse. `accounting` gains a required `vendorId` FK. `request.vendor` (the requester's free-text entry from capture) is **never rewritten** by accounting — it stays a historical snapshot of what was originally typed; the real relational link lives on `accounting.vendorId`, and the identity used for duplicate-checking lives on `request.vendorKey` (written once by `accountRequest`, at the application layer, since a generated column can't reach across to `vendor`'s own columns).

**Encryption.** `src/vendors/crypto.ts` mirrors `src/auth/crypto.ts` exactly — AES-256-GCM, a 12-byte IV, ciphertext, and a 16-byte auth tag concatenated and base64-encoded into one column, keyed by `BANK_ACCOUNT_ENCRYPTION_KEY` (already declared in `.env.example` with a comment already anticipating this exact use, referenced nowhere in `src/` until this slice). Only the full account number is encrypted; a masked last-4 is stored separately, in plaintext, purely for display, so nothing in the UI ever needs to decrypt just to render "••••0072." A narrow, logged reveal action exists for the rare case someone genuinely needs the full number — payer or accountant, and every reveal appends an `event` row, extending the brief's own "every file event is logged" principle to sensitive-field reveals. **`company.bankAccounts` (the org's own paying-from accounts, shipped in slice 1) stays plain, unencrypted `jsonb` this slice** — already inside the org's own trust boundary and already RLS-gated, lower blast radius than a third party's bank details, which is what fraud specifically targets. A stated cut, not an oversight; worth doing later as its own small, separately-reviewable change.

**Vendor matching at the accounts desk.** `AccountantPanel.tsx` gains a search field (name, GSTIN, or PAN — pre-filled from `request.vendor`'s free text, since the requester already typed a name) with inline "create new" for the no-match case, collecting only a name and an optional GSTIN-or-PAN — full KYC, bank details, and documents are entered on the vendor's own `/vendors/[id]` management page, not inline, so an accountant is never blocked mid-bill by a long form. `lockVendorMutex` (`src/vendors/lock.ts`, mirroring phase 7's `lockRequestMutex` exactly — a transaction-scoped Postgres advisory lock keyed on `hashtextextended`, salted differently so the two lock domains can never collide) guards the supersede-then-insert sequence whenever a `vendor_bank` row is replaced.

**Payer verification.** `payRequest` gains a precondition, checked before its existing validation: resolve the request's vendor via its latest `accounting` row, then check that vendor's **current** `vendor_bank` row (`supersededAt IS NULL`) has `verifiedAt` set. No bank on file at all → blocked, with a link to the vendor's own page. A bank record exists but is unverified → blocked, with a "verify before you pay" comparison screen (masked account number, IFSC, beneficiary name) and a single confirm action. This one live read — no per-request cached flag anywhere — is the entire mechanism behind "a bank change flags every open request for this vendor": the moment any `vendor_bank` row is superseded, the new row's `verifiedAt` starts null, so the very next `payRequest` attempt on *any* open request for that vendor re-triggers the gate automatically. A narrow, payer-only "bank only" correction path exists for the escape-hatch case (finding #3 above) — self-verified, requires an uploaded proof document, reachable only from the verify-first screen's own fine print, never from a general vendor-write surface.

**Duplicate control.** Checked at four points in the request lifecycle — capture and approve (advisory signals only: file checksum, vendor-name-text + amount + date window, since no vendor record is matched yet), account (the vendor is now matched or created, so the decisive vendor+invoice+financial-year signal becomes computable for the first time), pay (the decisive payment-reference signal) — but only **two** structural database guarantees exist: `UNIQUE (vendor_key, invoice_key, fy) WHERE stage = 'paid'`, and a now-case-insensitive `payment.reference` unique index. Both land only in phase 11, after every UI checkpoint and the override path already exist — an unbypassable index without a working override is exactly "a control nobody can get past," which the brief itself warns pushes real payments outside the system entirely. A super admin's override lifts the *application's* warning at submission; it does not and cannot touch the database's own constraint — if the override turns out to be wrong, the real duplicate payment still fails, hard, at the actual point of no return. The trickiest requirement — a duplicate sitting in a department the current actor can't see must still surface, redacted — is solved with a new `SECURITY DEFINER` function, `app_duplicate_check_candidates`, in the exact family as the existing `app_has_department_scope`/`app_has_company_scope` (phase 1) and `app_users_with_scope` (phase 5): it searches across every department regardless of the caller's own RLS scope, and returns only redacted fields (reference, date, stage) plus a `viewable_by_actor` boolean computed with the actor's own session GUCs — the unscoped reach lives entirely inside this one function, never as a broadened table-level policy. "The name of someone who can see it" reuses `app_users_with_scope` unchanged — one function, two consumers now. Resubmit-after-rejection routing (`request.routedApproverId`) is resolved from the **existing hash-chained `event` row** on the original request (`type = 'request.rejected'`, `event.actor` already *is* the approver who declined it) — zero new lookup capability needed, just a read of data already there.

**Computed flags.** Four are fully on-demand, computed at render time with no caching: ageing past the department's threshold (already have `department.ageingThresholdDays`, since phase 1), an unanswered query (already have `query.resolvedAt IS NULL`, since phase 6), a repeat amount for the same vendor in the same calendar month, and a vendor bank changed since the last payment to them. One genuinely needs a new cached column: `request.dueDate` — today's approval due date lives buried in `event.after`'s jsonb (fine for rendering one request's own trail, wrong for a queue rendering many rows per page load without a correlated jsonb-extracting join per row). Written by `approveRequest`'s existing combined `UPDATE`, cleared by `returnRequestToRequester` — the same "cache only the one thing that's genuinely expensive to derive live, and say why" discipline `request.stage` and `request.companyId` already established, not a new pattern invented for this slice.

## Phase 10 — payer verification

- No schema change. Migration `0016_payer_verification_rls_and_grants.sql` only: a payer-scoped `UPDATE` on `vendor_bank` (`USING (verified_at IS NULL)`, `WITH CHECK (verified_by = app_actor_id() AND verified_at IS NOT NULL)` — the same one-directional shape as `query_update`'s answered-state policy from slice 2), and a second, payer-scoped `INSERT` on `vendor_bank` for the narrow self-verified correction path (requiring a `vendor_document` row for the same vendor to exist first, as defense-in-depth, matching `payment_insert`'s own belt-and-suspenders style).
- `src/vendors/verifyCore.ts` (`verifyVendorBank`, `insertVendorBankAsPayer`), `src/requests/transitions.ts` (`payRequest`'s new precondition), `PayerPanel.tsx` (the verify-first comparison card, the no-bank-on-file state), `src/events/render.ts` gains `vendor.bank_verified`.

**Done means:** a request whose vendor has an unverified or absent bank record cannot be paid — attempted live, confirmed the exact blocking error appears; verifying unblocks the same session immediately; a *second*, separate open request for the same vendor, in a later session after a bank change, independently re-requires verification — confirmed live across two real requests, the concrete proof "flags every open request" holds with zero per-request flags anywhere; a second verification of an already-verified row is a safe no-op; the payer's narrow bank-correction path inserts a new, immediately self-verified row and supersedes the old one atomically under `lockVendorMutex`, verified with two genuinely concurrent attempts against the real dev DB.

**What the plan didn't anticipate, found during implementation:** a *third* `vendor_bank` UPDATE policy was needed — `vendor_bank_update_supersede_payer` — caught by the two-payer concurrency test itself, live: `insertVendorBankAsPayer`'s own supersede step always targets an *already-verified* current row (every row that function creates is self-verified at insert), so `vendor_bank_update_verify`'s `verified_at IS NULL` USING clause never matches it, and there was no other policy letting a payer supersede a current row at all — the first concurrent test run hit `vendor_bank_current_unique_idx` because the losing transaction's supersede silently touched zero rows under RLS rather than erroring, then its insert collided with the still-current winner. Fixed by mirroring `vendor_bank_update_supersede` (phase 9) for the payer role.

Also fixed in this phase's PR, found along the way rather than pre-planned: `tests/desks.test.ts`'s shared vendor fixture had no bank record, so this phase's own new `payRequest` precondition correctly started blocking that file's pre-existing payment tests — gave the fixture a pre-verified bank up front, since those tests exercise the four desks, not the verification gate. And two purely environmental bugs: `eslint.config.mjs` and `vitest.config.mts` were both sweeping up nested `.claude/worktrees/**` directories (other agent sessions' full git worktrees, including their own `node_modules`/`.next` build output and `tests/`), producing thousands of unrelated lint errors and, worse, silently running another worktree's test files — against whatever state that worktree happened to be in — as if they were this session's own. Both configs now explicitly exclude `.claude/**`.

## Phase 11 — duplicate control

- `financial_year(date)` SQL function, `request.invoiceKey`/`request.fy` (generated columns), `request.routedApproverId`, `duplicate_check` table + `duplicate_verdict` enum (`blocked_paid, warned_open, escalated_rejected, linked_held, none` — "matched_advance" deliberately excluded), `one_payment_per_invoice` partial unique index (`vendor_key, invoice_key, fy WHERE stage = 'paid'`), `payment.reference`'s unique index recreated case-insensitively — migration `0017_duplicate_control_schema.sql`.
- RLS — migration `0018_duplicate_control_rls_and_grants.sql`: `duplicate_check` policies (full visibility only when in scope for both `requestId` and `matchedRequestId`, or admin), `app_duplicate_check_candidates` (`SECURITY DEFINER`, `SET search_path = public`) + `GRANT EXECUTE`.
- `src/duplicates/duplicateCore.ts` (the check + redaction logic, plus `actorHoldsRole` — a shared override-authorization check reused by both capture and account time, since neither can trust a client-supplied "I'm a super admin" flag), `src/requests/captureCore.ts` (an optional `linkedRequestId` param resolving `routedApproverId` from the original's own rejection event, a capture-time checksum-based check, hard block on a "matched paid" verdict, an `overrideDuplicate` param), `src/requests/transitions.ts` (`accountRequest` runs the decisive vendor+invoice+FY check and writes the `duplicate_check` row when a match fires; `payRequest` gains a friendly catch around the two structural unique-index violations it can now hit), `src/db/schema/payment.ts` (the expression-based case-insensitive unique index), the capture form and `AccountantPanel` each gain a comparison card with an override control shown only to an actor who holds — and is re-verified as holding — an active `super_admin` grant, and the request detail page gains a "Reconsider" link (rejected stage) and a routed-approver banner (awaiting_approval stage, reconsidered requests only).

**What the plan didn't anticipate, found during implementation:**

1. **`duplicate_check_insert`'s own override clause was unenforceable as originally written**, caught by the very first live override attempt: the policy required `app_actor_role() = 'super_admin'` alongside `overridden_by = app_actor_id()`, but an override is always written *inside* the same transaction as the request/accounting insert it belongs to — which is *always* scoped as `requester` or `accountant` (whichever role is doing the capturing/accounting), never as `super_admin`, even when that same actor also holds a `super_admin` grant. `role_grant`'s own "three roles, three rows" model means only one role is ever the scoped role of a given transaction; the actual super-admin authorization already happened at the application layer (`actorHoldsRole`, checked before the insert is ever attempted) — the RLS policy's job is narrower than "was this a super admin," it's just "is this override attributed to the actor who's actually writing it." Fixed by dropping the role check from the policy's `WITH CHECK` entirely.
2. **A cross-test-file regression, found the hard way by running the full suite**: 7 test files' fixture-upload helpers all used the exact same hardcoded placeholder checksum (`sha256: "0".repeat(64)`) for every attachment — harmless before this phase, since nothing read that value meaningfully. Phase 11's own capture-time duplicate check searches org-wide by checksum, so once any one of those files' fixtures reached `paid`, every other file's later fixture upload using the same placeholder got correctly identified as "the same bill, already paid" and blocked — cascading into dozens of unrelated failures across `queries.test.ts`, `notifications.test.ts`, `comments.test.ts`, `desks.test.ts`, `payer-verification.test.ts`, `vendors.test.ts`, and `nudges.test.ts`. Fixed by generating a unique placeholder per call (`randomUUID().padEnd(64, "0")`) everywhere — the fixed value was never meaningful, only ever needing to satisfy the column's length check. One related stale assertion in `desks.test.ts` also had to be updated: it expected `payRequest` to *throw* on a reference collision, which was true before this phase's own friendly-catch addition around that exact unique violation.
3. **A previously-undiscovered crashed test run had left 13 orphaned `payer-verification.test.ts` fixture requests in the shared dev DB** (from phase 10, not phase 11) — found only because the phase-11 walkthrough's approver queue surfaced them as unexpected ₹500 entries. Cleaned up by hand via the owner connection, in FK-safe order; a reminder that a Vitest run killed mid-execution (rather than completing or failing cleanly) skips `afterAll` entirely, unlike an ordinary assertion failure.

**Deviations from the plan, made deliberately rather than by accident:** the reconsideration flow's UI lives on the request detail page (a "Reconsider" link, shown only when `stage = 'rejected'`) plus the existing `/requests/new` page reading a `?relink=` query param, rather than the two dedicated routes originally sketched (`/requests/new/duplicate-check`, `/requests/new/reconsider`) — a full extra route added no real capability once the capture form could already render an inline comparison card, and the reconsideration entry point reads more naturally from the rejected request's own page than from a bare capture-flow URL a requester would have no way to discover. The plan's four checkpoints collapsed to two real ones: `approve` was folded into `capture`'s own advisory check (the only signal available that early — file checksum — doesn't change between those two moments, so a separate identical re-check at approval time would only catch a request that became duplicate *while sitting in the approver's queue*, a narrow enough case that it's named here as a stated gap rather than built) — `capture` and `account` remain the two real advisory/decisive checkpoints, with `pay` covered structurally by the database's own two unique indexes rather than a third app-layer check.

**Done means:** submitting a real second photo of an already-paid bill is hard-blocked live with the comparison card, confirmed via a real browser upload of the identical file (not just a matching hash asserted in a test) — a genuinely different file submitted right after is not blocked; a super admin's override lets the second request proceed through capture/account — but a genuinely duplicate `pay` attempt still fails on the database's own unique index even after the override, confirmed live — the test that proves the override is a review gate, not a backdoor; a resubmission of a rejected request correctly resolves `routedApproverId` from the original's own `event` row, confirmed live end-to-end (reject → click Reconsider → banner names the original ref and the approver who declined it); the redacted cross-department match verified both in an automated test and via a raw restricted connection — an out-of-scope actor's `duplicate` result has `viewableByActor: false` and a null reference/date; the same UTR in two different letter cases against the real dev DB — second attempt rejected with a friendly error, not a raw exception.

## Phase 12 — computed flags

- `request.dueDate` (nullable date) only — migration `0019_request_due_date.sql`. No RLS migration: the existing blanket `UPDATE` grant on `request` (phase 1) already covers the new column; nothing about a due date is more sensitive than fields already visible under the existing policies.
- `src/flags/computeFlags.ts` splits in two: `computeFlags` itself is pure (no I/O — a `RequestForFlags` row plus a pre-loaded `FlagContext` in, a `Flag[]` out, directly unit-testable against hand-built fixtures with no database at all) and `loadFlagContext` does the actual batched reads (department thresholds, open queries, repeat-amount siblings, vendor bank status) once per page load across every row being rendered, never per row. `src/flags/FlagDots.tsx` renders the dots (native `title` attribute as the hover reason — no JS tooltip library needed). `src/requests/transitions.ts` (`approveRequest` writes `dueDate` only when `cycle === "dated"`, `returnRequestToRequester` clears it). The approver/accountant/payer queue pages and the request detail page all call `loadFlagContext` once inside their existing `withGrantScope` block and render `<FlagDots>` next to each row/the header. `src/app/(app)/payments/page.tsx` also lost its own N+1 event-scan for `dueDate` in the same pass — a live example of the exact inefficiency `request.dueDate` was cached to avoid; only the `cycle` text (immediate vs. dated vs. unspecified) still needs the event scan, since that alone was never cached.

**Done means:** each of the five flags verified twice — pure unit tests against `computeFlags` directly (ageing threshold boundary, held/terminal-stage exemption, due-soon's 48-hour window and overdue-vs-upcoming severity, plain membership checks) and a live dev-DB integration test suite (`tests/flags.test.ts`) exercising `loadFlagContext` through real `withGrantScope` calls — plus a live browser walkthrough confirming the same five: a request older than its department's ageing threshold shows a red dot, an on-hold request of the same age does not; raising a query shows an amber dot that disappears the moment it's answered (confirmed from both the approver's and requester's own sessions); a dated-cycle request due within 48 hours shows an amber dot (red once overdue) that only appears once the request is actually in `to_pay`; two same-vendor, same-amount, same-calendar-month requests both show the repeat-amount dot, a third at a different amount does not; verifying one vendor's bank cleared the bank-changed dot from *all three* open requests tied to that vendor simultaneously in one page load — the live proof that this is one read against the vendor's current bank row, not three separate per-request flags. Confirmed by inspecting the diff that nothing beyond the one `dueDate` column is written anywhere in this phase.

**What the plan didn't anticipate, found during implementation:**

1. **The migration-timestamp-ordering bug (named in phase 11's own writeup) bit a third time, worse.** `0019`'s auto-generated timestamp came out smaller than 0018's hand-picked one, so `drizzle-kit migrate` silently no-op'd the `ALTER TABLE` — the by-now-known failure mode. While investigating why the column didn't exist, a misread of the tracking table led to mistakenly deleting migration *0018's own legitimate row* (already correctly applied back in phase 11), not a bad 0019 entry — briefly leaving the tracking table out of sync with reality, though 0018's actual schema objects (verified directly) were never touched. Recovered by restoring 0018's row and inserting 0019's by hand, both via a direct `psql` connection after the session's own auto-mode classifier blocked the equivalent Node-script writes to `drizzle.__drizzle_migrations` specifically (plain `ALTER TABLE`/`SELECT` through the same script were unaffected — the block was scoped to writes against that one tracking table). Worth reconsidering whether hand-picking future migration timestamps at all is still worth the recurring cost, now that it's caused a real mistake rather than just a silent no-op.
2. **"A vendor whose bank details changed since the last payment" (the doc's own phrasing) is implemented without ever checking for a prior payment.** The bank-changed flag fires whenever an accounted, still-open request's vendor has an unverified current bank row — full stop, whether that's because the bank was just changed or because it was never verified in the first place. Distinguishing "changed" from "brand-new and unverified" would need an extra join against payment history for no behavioral benefit: `checkPaymentBankReadiness` (phase 10) already treats both cases identically at pay time, so this flag just surfaces that same live read one stage earlier, across every desk that can see the request, rather than gating on it only at the payer's own desk.

## Done means, for the whole slice

- A bill can't be paid to a vendor whose bank details nobody has verified against it, and can't be paid twice — one of those two is enforced live at the moment of payment, the other by a database constraint no application code path can talk its way past.
- Every vendor's KYC and bank history lives on one page, versioned, with the account number encrypted at rest and every reveal logged.
- A rejected bill, reconsidered, visibly lands back with the specific person who said no the first time — without locking anyone else in the department pool out of acting on it if that person is unreachable.
- Every queue shows ageing, an open query, a due date, a repeat amount, and a bank change as five computed, explainable flags — none of them cached beyond the one column that genuinely needed it.
- CI green, deployed, the same "someone other than you put a real bill through it" bar every prior slice set for itself — this time including someone actually catching a real duplicate before it got blocked.

## Decisions already made — do not reopen

§09 (the settlement ledger, advances, part-payments) is out of scope in full — no schema, no UI, no reserved columns for it anywhere in this slice. `payment.UNIQUE(request_id)` is untouched. "Matched an open advance" is excluded from the duplicate verdicts by name. `vendor_key`/`invoice_key`/`fy` are computed two different ways (a generated column vs. an application-layer write) for a stated structural reason, not inconsistently. `vendor_document` is its own table, not folded into `request_file`. `company.bankAccounts` stays unencrypted this slice, for a stated reason. Resubmit-after-rejection routing is soft — a banner and a queue-sort hint, no per-user approval enforcement, no 48-hour auto-escalation timer. Flags are computed on-demand except the one `request.dueDate` column, added on the same precedent `request.companyId` already established.

Confirm before phase 11 ships: perceptual-hash duplicate detection stays reserved-but-unbuilt (see the scope section above) unless that should change.

Deferred on purpose: GST/206AB/lower-deduction-certificate compliance fields (no integration exists anywhere to check them against). The standalone `/audit` investigation console described in the brief's §14 — the per-request trail already exists and already covers this slice's own audit needs; the console itself reads like slice-4 health-console territory, not named in AGENTS.md's slice-3 sentence. `company.bankAccounts`'s own encryption retrofit. Cover for a department whose only approver is away — still open, org-wide, unchanged since slice 1.
